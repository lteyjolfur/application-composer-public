Every job application wants a slightly different CV. A frontend role should lead
with UI work; a fullstack role with integrations; a lead role with mentoring.
Rewriting the same achievements by hand for each one is slow, and copying an old
CV is how the wrong company name ends up in a cover letter.

[Application Composer](https://github.com/lteyjolfur/application-composer-public)
is my answer: write each achievement once, tag it, and let a small script pick the
right ones for each job.

![A CV page generated by Application Composer from fictional sample data]({{ "/assets/example-cv.png" | relative_url }})

## Plain files, on purpose

Everything is YAML or Markdown in a Git repository: a profile, work history,
skills, a bullet bank of achievements, and one folder per application. There is
no database, no web UI, and no network call. That was a deliberate constraint:

- **The data is the product.** A CV is only as good as its bullets, so the bullets
  should be easy to read, edit, and review in a normal editor and in `git diff`.
- **It runs offline and forever.** Nothing to host, nothing to log in to.
- **Every output is traceable.** Each application folder keeps the job ad, notes,
  the tags used, and the generated CV and letter together.

## Choosing bullets with tags

Each bullet in the bank carries tags such as `frontend`, `payments`, or
`mentoring`. A *variant* (frontend, fullstack, leadership, test automation)
lists the tags it cares about, and an application can add or exclude tags on
top.

```yaml
# applications/acme-frontend/selected-tags.yaml
company: Acme
role: Frontend Developer
variant: frontend
tags: [accessibility]
exclude_tags: [payments]
pin: [design-system-migration]
```

Selection is deliberately simple and explainable:

1. Pinned bullets go in first.
2. Every other bullet scores the sum of its matching tags, with a few tags
   weighted higher. Bullets with an excluded tag are dropped.
3. Section quotas (experience, impact, leadership) keep the mix balanced, and a
   cap keeps the CV short.
4. Near-duplicates are skipped: if one bullet's normalized text contains
   another's, only the higher-scoring one is kept.

I considered smarter matching and chose not to. When a CV comes out wrong, I want
to see *why* in thirty seconds, and the fix should be "improve the bullet or its
tags", not "tune a model".

## Validation that fails loudly

The most useful script is `npm run validate`. It checks every file and lists
every problem at once: an unknown tag, a duplicate bullet id, a pinned bullet that
doesn't exist, a bullet linked to a job that isn't in the work history. The rule
for the project is that validation must never become a success-only stub.

Two later additions follow the same idea:

- **JSON Schemas** for the YAML files, so VS Code autocompletes fields and
  underlines typos like `summery` while I type.
- **A placeholder check before export.** `npm run export` refuses to produce a PDF
  while `<COMPANY_MOTIVATION>`, an `[EXAMPLE]` bullet, or template text is still in
  the document, and lists each one with its line number.

## Testing what matters

The test suite (Vitest) focuses on behavior a user would notice: which bullets are
selected, where they appear, what validation rejects, which names the command line
refuses. Integration tests build a whole CV from a small fictional data set, so
they keep passing when I edit my real data.

A review pass deleted tests that only pinned implementation details, and one that
asserted a known limitation (reworded duplicates aren't detected), because a test
like that turns a future improvement into a failure.
